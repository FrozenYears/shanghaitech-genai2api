# 下一阶段：消除空转与完成长程交付

状态：原分析/实施计划保留；随后用户已授权显式客户端任务模式试点，最小实验、执行状态元数据修复、TaskClient/CLI及初版失败迭代见[实验记录](STALL_EXPERIMENTS_2026-11-08.md)。尚未据此宣称从头连续长测或默认客户端核心问题全部解决。前阶段事实见[阶段记录](LONGRUN_PHASE_2026-11-08.md)。

## 1. 核心决策

项目价值以真实任务完成衡量，而非“代理正确返回错误”。空转、重复叙述、只给计划是P0核心问题；上下文完整与工具协议可靠是同一目标的前置条件。不得把模型能力、平台不可用或auto协议约定当作跳过架构研究的理由。

实施路径优先级：**可定位证据→上下文/协议根因→明确行动与结束控制→客户端闭环→受控短测→自然长测**。不先重复跑数小时长测，不靠增加预算/提示长度/关键词拦截证明改进。

需要区分三种成功：

1. 传输成功：字段/SSE与终态正确，未丢工具批次。
2. 执行成功：客户端真正执行且拿到关联回执。
3. 任务成功：全部所需产物与独立验收通过，权限/阻塞/待完成事项没有被掩盖。

前两项通过不能代替第三项。

## 2. 验收标准与反例

### 2.1 观察分类

- **非预期停止**：已知还有可执行待办、工具权限和必需输入可用，却以无调用计划/承诺正常结束。必须由任务契约、独立验收或可审计状态判定，不仅靠句子像不像计划。
- **无进展循环**：同一未完成目标下重复观察相同状态、重复失败操作或重复说明，没有新增有效证据/操作效果。读取本身可能是必要进展；相同路径内容变化不能误判。
- **合法终答**：普通问答，或全部工作已验收完成。不能为了防空转强行制造工具调用。
- **合法等待/阻塞**：任务已交付后台且有对应job、缺权限/外部输入/平台不可用，需明确状态并保留恢复点，不能虚构进度或无限自激请求。
- **真实推进**：执行必要操作、解决一个失败检查、取得与调查有关的新证据，或完成正确的等待→结果→续作转换；不以工具数量/文件大小/文字长度计进展。

### 2.2 候选上线前必须满足

| 条件 | 可失败信号 | 不能替代它的指标 |
| --- | --- | --- |
| 上下文完整且可对照 | 关联ID、参数、结果、错误标志、角色/顺序或附件摘要不一致 | “总token差不多”“模型说记得” |
| 未完成执行任务能继续 | 只给计划后没有有效下一步，或同状态重复循环 | HTTP200、stop、工具数增长 |
| 合法问答与完成能结束 | 被强制调用无关工具、无法完成终答 | 任务模式样本通过 |
| 工具调用可靠 | 坏批次泄漏/误执行、纠错丢参数或混入历史调用 | 解析器能抽到某个JSON |
| 中断与副作用安全 | 重放已执行操作、同时发两次prompt、无回执就宣称成功 | 重试最终得到一个答案 |
| 真正长程完成 | 所有阶段的累计业务/工作流/交付门禁通过 | 分段累计、局部PASS、控制器代跑 |

发布门槛使用指定样本全量通过，不将有限样本表述成任意场景100%可靠；出现失败就保留并定位，不删用例或改预期取巧。

## 3. 优先可证伪假设

以下是调查方向，不是已确定根因。

| 优先级 | 假设 | 只改变什么 | 预测与否证 |
| --- | --- | --- | --- |
| H1 | 原目标/最新指令在tool转user、chatInfo抽取与Schema追加后被弱化或错位 | 只改变当前轮布局，保留全部历史和参数 | 相同失败状态下新布局更稳定产生所需操作；若输入已经正确且对照无改善，则降级 |
| H2 | 多套工具表示和冗长/冲突指令使模型把协议当作文书 | 只改协议提示的单一表示/示例/精简，与现行严格解析保持一致 | 坏外壳和无调用计划下降，正常终答不退化；不能靠放宽解析获得假改善 |
| H3 | 控制层没有区分行动、等待、阻塞、终答，导致未完成计划直接stop | 在显式任务模式试验明确决策契约/完成握手 | 已知待办时必须选择可执行动作或真实阻塞，不把所有auto问答改required |
| H4 | 同样的“继续”反馈重复灌入，没有更新可执行的当前状态 | 只改反馈内容与状态摘要/下一步约束，不增加预算 | 同一停滞样本能转入新证据/操作；若仍重复，不能再靠增加反馈次数 |
| H5 | 运行时工具能力/工具结果编码不完整，任务要求与可用权限不一致 | 固定同一权限且核对真实能力、错误与后台终态表示 | 减少因能力缺口导致绕行；能力齐全仍只计划则不能归因权限 |
| H6 | 学校平台对历史角色/长消息的消费或缓存存在差异 | 固定目标和工具，独立变化历史内容/布局/长度，绕relay/经relay对照 | 原始网页输入输出与双跳差异可定位；不能仅凭耗时或一次复述推断缓存 |

本轮无网络构造探针已执行：`system/user/assistant/tool`经第一跳变为`system/user/assistant/user`；`chatInfo`含最后工具结果和当前Schema，不含原目标，而原目标仍在`messages`历史中，`is_error=true`也保留。此结果证明当前布局，**不证明目标已经丢失**，更不证明学校如何分配注意力；H1需用真实网页同状态布局对照继续检验。

两项独立研究已交付并由主线程阅读：

- 上下文审计确认多条工具结果的顺序会改变`chatInfo`及Schema所附宿主；三种直连接口与relay统一Chat路径并不语义等价。第一跳重建带调用assistant时丢弃顶层历史思考元数据，工具包装不承载content以外的额外job/details。这些是本地变换事实，是否导致实际停顿须用最小对照证明；不能盲目回灌思考或把所有额外字段塞进提示。
- 第一手实现对照支持将行动、候选终答、等待与阻塞分开控制，而非永久required：[OpenAI Agents](https://openai.github.io/openai-agents-python/agents/#forcing-tool-use)明确有工具选择重置以避免循环；[Pydantic AI输出函数](https://ai.pydantic.dev/output/#output-functions)允许显式终答与验证重试。它们提供设计参照，不证明本项目模型具备相同原生工具能力。

综合决定：下一轮先完成H1/H2的端到端可观察对照与已证有损adapter修复，同时准备显式任务决策候选；若上下文/提示单点修正不能提高真实交付，不再无期限优化提示，转向带可信完成/阻塞状态的客户端任务控制试点。候选B/C需说明兼容变化后ask，不能用“auto规定如此”回避解决，也不能未经许可暗改所有客户端。

## 5. 实施阶段与逐关验收

### A. 证据基座与最小失败循环

1. 从已有Kimi第30阶段抽取最小必要上下文、工具定义、工具结果、计划stop；原文件保持不动。
2. 在四个seam观测同一请求：客户端入口、relay出站、第一跳网页载荷、学校原始输出及最终工具事件。脱敏后只保存必要字段；以规范化结构摘要核对，不打印密钥/base64/完整文档。
3. 明确每个变化是有意adapter变换还是丢失/歧义；三协议都核对。图片/文档保持原轮次、像素或内容摘要，不通过清历史使样本“成功”。
4. 产出一条能红/绿判断“未完成却无操作结束”的命令。没有这个循环，不开始大规模架构修改。

### B. 上下文和工具契约修复

- 先修已证的丢失、错序、含糊成功/失败、角色消费不一致和当前目标错位。
- 统一请求级语义，模型ID不硬编码；不为Kimi单独拼临时规则掩盖通用缺陷。
- 提示精简候选必须与当前提示做对照，不继续无验证叠规则。
- 工具格式从生成约定、增量识别、终态解析、Schema反馈一起验收；保持严格校验与整批拒绝，不靠不断特判新字符串宣称彻底解决格式问题。

### C. 行动与结束控制候选

研究至少三种设计，不提前选定实现：

1. **兼容auto的布局/生成约定修复**：成本最小，保持普通问答；若仍不能稳定区分行动与终答，不继续无限调提示。
2. **显式任务执行模式**：任务未通过独立验收时，允许行动/等待/明确阻塞/提出完成申请；完成申请必须由客户端任务状态确认。不能代理自行读取本地业务文件；没有验收器时只能报告未验证。
3. **客户端任务控制器**：承担完整任务账本、结果归属和停滞策略；两跳仍负责无损传输与请求级生成。让普通客户端通过明确接入获得能力，而不只在隐藏测试runner里有效。

首选待实验决定；不同时叠三套恢复。必须明确唯一重试所有者、各类预算和不可重放状态，任务总预算不能因每次新请求重置。应保留客户端已有的task/job异步语义，而非用通用“继续”取代。

### D. 小样本对照与消融

先固定12类场景，再为每类至少准备一个不同表述/顺序的保留样本；两模型各重复3次，记录全部结果。失败样本重放与自然生成分别统计，首次失败不靠重跑覆盖。

1. 简单创建→回读→结束；2. 修改→真实测试失败→修复；3. 多文件依赖实现；4. 长历史后明确待办；5. 显式失败工具结果；6. 坏封套/尾部正文/参数缺失；7. 重复读同内容但任务未完成；8. 同路径内容变化应重读；9. 后台启动→完成→续作；10. 问答无需工具；11. 已完成任务正常终答；12. 权限拒绝/真实外部阻塞/取消（独立子例）。

比较顺序：当前基线→仅上下文修正→仅控制候选→必要组合；单次只改一个变量。记录失败是否转移到其它层，不只看调用数增长。

### E. 自然长期任务与客户端实用性

- 两模型分别从头30阶段、新目录、新连续会话。正常样本禁用人工“继续”和临时源码接管；协议自纠错、任务控制反馈和平台恢复分别统计。
- 加入至少一个未照抄账本题的交付任务：已有多文件工程修复+文档/清单，保证所有所需操作实际有权限。
- 每阶段既核对独立业务，也核对最后改动后的真实执行和完整交付；最终人工审阅语义文档，不以存在/非空/自报PASS代替。
- 平台不可用独立列为基础设施失败，不充当模型/设计优劣证据；运行中不得因失败临时加预算、删用例或改验收标准。
- 通过真实普通客户端接入候选能力再验一次，不能只证明自定义runner能跑。omp优先；Claude Code/Responses客户端在目标接口可用时验证，未覆盖明确列出。

## 6. 指标与失败记录

必须记录：有效执行任务完成率、非预期零调用stop次数、连续无进展轮数、协议自纠错成功/失败、重复工具输入及真实结果变化、普通问答误强制操作、完成后重复动作、副作用重放、首正文/首有效工具时间、任务级反馈、人工干预、模型请求/学校生成尝试、独立检查与模型执行回执。

- 所有分母和计数范围固定；缺原始学校HTTP计数就写未统计，不从模型请求推算。
- 工具输出格式“解决”须在声明支持的协议集合、未知外壳、截断与引用反例上验收；不是承诺任意损坏字符串都能执行。
- 完整历史“解决”须证明客户端发来的受支持信息被保留且学校可消费；客户端从未发送的信息不能凭空恢复。此事实不能作为不修既有有损adapter的借口。

## 7. 必须先ask的设计变化

| 变化 | 用户需要知道的代价 |
| --- | --- |
| 把默认auto改为强制行动/终答握手 | 普通问答/现有客户端可能不兼容，必须提供真实负对照 |
| 新增任务状态/服务端持久会话 | 数据保存、并发、恢复、隐私及现有无状态部署语义改变 |
| 默认接管普通客户端自动续作 | 增加请求/耗时/费用，可能产生意外副作用，需取消与权限控制 |
| 大范围缓冲/撤回正文或取消流式 | 延迟和交互语义改变；当前不计划取消流式 |
| 改工具执行权、放宽权限或执行模型损坏参数 | 安全模型改变，不得默默扩大 |
| 引入上下文摘要/压缩/删历史/清附件 | 可能损失工作状态；不能以删内容换“稳定” |

本轮不请求这些变更的提前空白授权；研究和最小实验拿到实证后，带明确方案与对照结果再问。保守的无损修复、现有接口内的正确性修复按原约定执行。
