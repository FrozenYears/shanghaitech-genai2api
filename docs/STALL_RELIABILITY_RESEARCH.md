# 空转与长程交付可靠性：恢复边界和第一手实现调查

## 1. 范围、证据等级与结论

本轮仅做源码调查和下一阶段设计，不修改运行代码，不安装依赖，不运行测试、模型长测或服务重启。阶段事实沿用[阶段记录](LONGRUN_PHASE_2026-11-08.md)，没有重新读取完整原始会话、凭据或模型工作区。

本文严格区分：

- **已证行为**：本仓库当前源码能直接证明的控制流，或阶段记录明确记载的实际结果。源码存在不等于真实链路已验证。
- **可证伪假设**：对空转机制的候选解释，尚未通过受控实验排除替代原因。
- **设计候选**：尚未实现、尚无效果数据，不表述为修复完成。
- **需用户许可**：改变 `auto`、完成协议、客户端控制权或持久任务状态的行为变化。

核心结论：**请求合法结束、任务验收完成、用户可以放心离开，是三个不同层次。** 当前请求层恢复解决空响应和未交付坏工具批次，不能凭借一次非空 `stop` 判断项目任务已经完成。任务级监督已经能够诚实拒绝假完成，但这不代表能够稳定推动下一步实际操作。[阶段记录第6节](LONGRUN_PHASE_2026-11-08.md#6-仍未解决的核心问题)仍是未解决问题，而不是“模型能力不足、架构无需再查”的结论。

建议优先顺序：**A：完整上下文/反馈的受控对照与最小提示修正 → B：选择性 action-or-finish 判决 → C：客户端任务完成握手与门禁**。A 的证据建设是后两者的共同前提；若 B 显示仅能增加调用数、不能提高真实交付率，应停止叠加提示，转向 C 的任务控制试点，而不是无限重试。

**不可混淆的三层 native：**

1. 对外 OpenAI/Anthropic/Responses 的结构化工具事件，是适配器的 transport 合同。
2. `provider/genai.py:323–395` 能接收上游 `delta.tool_calls`，说明存在原生形状的输出解析能力；[`provider/streaming.py:186–197`](../provider/streaming.py#L186-L197) 对这种输出与文本调用同样严格校验。
3. 本项目给学校模型的输入仍可由文本 Schema/ACTION 构成。**native structured transport 不等于模型 native 函数输入，也不等于模型原生训练工具格式已被正确启用。** 上游偶尔返回 `tool_calls` 也不能证明请求端已经传入原生函数定义。学校内部模板和模型接口需要另外的一手证据，不能凭对外 SSE 名称补全。

## 3. 第一手实现对照

以下读取的是项目维护方原始源码与官方文档，不用二手文章替代。外部链接指向调查时读取的 `main`，会漂移；本次 GitHub commit API 返回 403，未取得可固定的提交 SHA，因此不冒称不可变快照。下列外部行号依据实际 raw 读取；代码搜索索引行号可能滞后，复用时应按函数名重新定位。这里只将外部实现用作设计证据，**不将其做法视为本项目已证根因或效果证明**。

### 3.1 OpenAI Agents Python：工具后回到 auto，终答与工具终止策略分离

第一手证据：

- [源码 `maybe_reset_tool_choice`](https://github.com/openai/openai-agents-python/blob/main/src/agents/run_internal/tool_execution.py#L554-L563)：当 `reset_tool_choice=True` 且 tracker 确认使用过工具时，返回 `dataclasses.replace(model_settings, tool_choice=None)`。不是每一轮永久 required。
- [源码 `check_for_final_output_from_tools`](https://github.com/openai/openai-agents-python/blob/main/src/agents/run_internal/turn_resolution.py#L789-L821)：默认 `run_llm_again` 不把工具结果直接当终答；`stop_on_first_tool` 以首个工具输出终止；`stop_at_tool_names` 只在命中特定工具时终止；也允许回调返回 `ToolsToFinalOutputResult`。
- [源码普通文字终答分支](https://github.com/openai/openai-agents-python/blob/main/src/agents/run_internal/turn_resolution.py#L1308-L1334)：无结构化 output schema／普通文字 schema 时可形成最终输出，否则未终结时返回 `NextStepRunAgain`。这不是默认拒绝所有非工具回答。
- [官方 agents 文档：强制工具和工具使用行为](https://openai.github.io/openai-agents-python/agents/#forcing-tool-use)：明确提醒强制 tool_choice 在工具结果回到模型后可能形成无限调用，默认重置避免该循环；[官方运行说明](https://openai.github.io/openai-agents-python/running_agents/)说明最终输出、工具循环及 `max_turns` 边界。上述行为也经 Context7 的官方仓库文档检索交叉定位。

可借鉴：

- “本轮确定需要 action”与“整场任务每轮必须工具”是不同策略。即便做 scoped required，也要明确解除点；下一轮可能应普通终答、阻塞报告或等待已交付工具。
- `stop_at_tool_names` 可以表达经过可信完成工具后的终止，但任意 read/write 成功并不代表全任务完成。本项目不能照搬 `stop_on_first_tool` 作为交付成功。
- 回调掌握的完成依据比 JSON 外形重要：若完成工具只回显模型自述，门禁仍是假完成。

不能据此声称：OpenAI 框架默认就能发现用户工程交付缺失，或把同一份提示搬来就能消除本项目空转。

### 3.2 Pydantic AI：显式输出类型／输出工具、有限输出纠错、外部执行续接

第一手证据：

- [源码 `CallToolsNode` 的 action/output 判决](https://github.com/pydantic/pydantic-ai/blob/main/pydantic_ai_slim/pydantic_ai/_agent_graph.py#L3880-L3981)：提取文字、工具调用和其他内容；有工具调用时进入工具处理；只有配置允许的 text processor 才接受文字输出；没有可操作输出时构造 `RetryFeedbackPart` 并转回 `ModelRequestNode`。它不是仅以 provider 的 stop 字符串决定任务最终状态。
- [源码 `consume_output_retry`](https://github.com/pydantic/pydantic-ai/blob/main/pydantic_ai_slim/pydantic_ai/_agent_graph.py#L823-L848)：递增 `output_retries_used`，超过 `max_output_retries` 抛出 `UnexpectedModelBehavior`。输出验证与每工具重试预算分别管理，不是无限加“请继续”。
- [官方仓库 output 文档](https://github.com/pydantic/pydantic-ai/blob/main/docs/output.md#output-functions)：输出函数类似工具，但调用标志 run 结束，结果不再回喂模型；参数仍校验，可通过 `ModelRetry` 拒绝后让模型修正。同页明确允许 `str` 时普通文字可以终答，并有失败输出类型例子，而不是强迫所有问题执行外部动作。
- [官方 deferred tools 文档](https://ai.pydantic.dev/deferred-tools/)：需要用户批准或外部客户端执行时，可以返回 `DeferredToolRequests`；调用方携原消息历史和按 call ID 关联的 `DeferredToolResults` 再接续；批准拒绝是显式结果。说明“当前 run 返回”可以是等待外部结果，不等于整个任务成功结束。

可借鉴：

- 工具 action、候选 finish、阻塞／待批准输出可以成为明确的协议分支；输出函数可承载完成验证，不应把“像终答的文字”直接提升为已交付事实。
- 外部执行场景需要客户端参加状态机；仅在 provider 内继续生成，既拿不到新工具回执，也不能替客户端验收文件与批准状态。
- 结构化输出检查解决格式和状态可辨识性；业务完成仍需可信验收，不能靠输出 schema 的 `completed=true`。

不能据此声称：本项目已经使用这些输出模式，或把文本 ACTION 换成结构化 transport 就自动获得相同的模型约束。Pydantic AI 的 tool/native/prompted output 是不同能力路径，不能混为一谈。

### 3.3 对本项目的直接比较

| 维度 | 提示／上下文修正 | 显式 action-or-finish | 任务完成门禁与客户端 |
| --- | --- | --- | --- |
| 判定对象 | 模型看到的信息和执行指令 | 本轮要动作、候选终答还是阻塞 | 整个用户任务是否真正交付 |
| 普通问答 | 保持普通终答 | finish-answer 必须可达 | 不挂工程验收器，不误强制工具 |
| stop 后有限继续 | 仍容易只有新提示 | 不合约输出可有限纠错，合法 finish 不能直接冒称完成 | 独立未完成差异驱动有限续作；预算耗尽仍失败 |
| 已交付工具 | 以完整回执防误解 | action 分支只能发新调用，不能重放旧调用 | 客户端保存 pending/result，按真实状态续接 |
| 真阻塞／权限拒绝 | 提示明确允许报告 | blocked/needs-approval 分支，不得编造参数 | 保留阻塞原因并停止，不用继续计数绕过权限 |
| 实施边界 | 请求呈现层和恢复提示 | 需显式接入的控制协议 | 调用方／监督器，拥有验收和授权的主体 |

## 4. 可证伪假设：先划清观察，再检验机制

| 假设（均未证实） | 预测 | 反证／降级条件 |
| --- | --- | --- |
| H1：工具回执以 user 文本呈现、当前问题切分、协议重复与反馈顺序影响任务状态理解 | 在工具权限、完整历史、附件、预算相同条件下，仅调整呈现／反馈的对照能降低“未交付时非空计划 stop”，并提升真实交付 | 请求边界逐项等价且呈现变体不改善；或只减少计划文字、交付率不变。不能凭一次成功排除／证实。 |
| H2：auto 下非空文本合法导致缺少可辨识的“还在执行／候选完成／阻塞”决策 | 显式 action-or-finish 对照能在相同预算内增加与缺口相关的新动作，减少非法 finish，同时普通问答仍能终答 | 只产生无关 read、重复 action 或伪 finish；多工具但交付不改善，说明仅改变输出外形不足。 |
| H3：恢复反馈有差异但没有任务级可执行状态转换，形成相同策略循环 | 使用可信任务差异、pending 回执和明确下一状态的客户端门禁，比重复续作提示减少停滞并提高独立验收通过率 | 门禁只更快拒绝假完成，仍无下一步有效动作／仍预算耗尽；这是诚实失败改善，不能算可用性成功。 |

各假设可以同时成立；实验须逐变量变更，不把学校 worker 故障、工具权限变化、人工扩预算或新会话复制工作区混入方案收益。

## 5. 三个候选方案与优先顺序

### A（优先1）：保持 auto，验证上下文语义并做最小提示／反馈修正

**设计候选：**先把当前问题、完整消息序列、tool call/result 关联、附件、协议块的位置和恢复附加文本做定向边界对照；只记录必要的计数、类型和摘要，不采集凭据或完整日志。对照确认具体问题后，再只改对应角色说明、任务锚点或恢复反馈的位置／去重。任务状态摘要只能补充完整历史，不能替换、裁剪原历史或附件。

- 得：最小行为变更，保留普通问答终答、流式和现有客户端；能区分“信息没到／表示失真”与“到达但仍不行动”。
- 失：当前提示已有“勿只给计划”；继续堆指令可能加重冲突。单靠提示没有强完成边界，不能保证防止非空计划 stop。
- 可证伪实验：固定未完成任务起点、原历史和工具回执，比较原提示与单一呈现修正；采集首次相关有效动作、连续计划 stop、真实交付、重复副作用、预算消耗。若仅文字更积极、交付不提高，拒绝“已修复”结论。
- 许可：本轮仅记录。实际新增数据采集、日志保留或运行真实模型对照前需明确范围；若修正引入状态存储或改变工具语义则另行许可。

### B（优先2）：选择性 action-or-finish 判决，拒绝“只有计划”的第三种含混状态

**设计候选：**仅在显式加入该协议的客户端任务上，要求每个控制节点在以下状态中选择：`action`（完整合法新批次）、`finish-answer`（普通问答）、`finish-candidate`（行动任务请求验收）、`blocked`（缺信息／真实外部条件）、`needs-approval`（权限门槛）。这些名字是设计说明，不是当前接口字段。不得私自把普通文字中的计划识别为可执行工具，也不得猜未知参数。

- 实施可以是一次明确的状态输出协议，或在可信未完成状态下**局部、有限、显式地**用现有 required；后者只适合确实可继续且具备参数与权限的下一步。需要终答、阻塞或等待回执时必须解除，不采用全局 required。
- 得：把“我接下来会做”从合法候选完成中分离；可直接统计错误决策，有限纠错有明确终止点。
- 失：额外判决可能同样被模型敷衍；格式正确不代表动作有效。若只有 action 没有 blocked/finish，会诱导无用工具、参数臆造或无限调用。额外调用也增加时延与故障面。
- 与请求级恢复的边界：provider 只修尚未交付的合约错误；一旦合法 action 已交给客户端，必须结束本次工具交付、等待其回执。不能 provider 内反复要求“重发 action”来冒充任务继续。
- 可证伪实验：固定 A 的上下文基线，对比 auto 与显式判决；分别检查问答、可执行缺口、未知参数、权限拒绝、待完成后台工具、已经成功写入回执。若 action 率上升却交付不升，或出现误强制工具／重复副作用，则不接受 B 为有效方案。
- 许可：必须先向用户说明它会改变终答和 auto 的使用方式；默认客户端不变。没有许可不加隐藏控制工具、不改现有 ACTION grammar、不吞掉用户原本应收到的合法 stop。

### C（优先3，长期交付目标）：客户端可选任务控制器＋可信完成握手

**设计候选：**在真正掌握工作区、授权、工具结果和验收的客户端接入任务控制，而不是让通用 provider 擅自执行工具。复用现有 supervisor 的有限预算、停稳约束、验收和回执关联；把“仅追加反馈”升级为明确任务状态转换。候选终答是申请完成，不是完成事实。

最小握手语义：

1. 客户端显式声明这是需要交付的任务、验收范围和预算；普通问答不被默认改为工程任务。
2. 模型输出 action，由客户端执行；已交付、运行中、结果未知、已成功、失败分别记录。call ID 关联不是跨崩溃 exactly-once 保证，未知副作用结果时应暂停核对，不能自动重放。
3. 模型提出 finish-candidate 后，客户端待所有相关工具真实停稳，核对真实回执和独立验收；通过才发布任务完成事件。安全正文仍即时流式，可显示“候选完成、待核验”，不回滚已显示内容。
4. 失败时回馈实际缺口，有限继续；重复动作必须结合工具输入、实际输出、工作区／验收状态判断，不能仅按同一命令或路径禁止。
5. 真实阻塞、用户取消、权限／身份拒绝、无法证明停稳或预算耗尽均可合法停止，但状态不能标为成功；待批准是等待用户，不是自动重试授权。

- 得：直接面向“交付而非像完成”；客户端可把 pending、真实阻塞和完成区分开，避免 provider 越权。
- 失：客户端必须接入；通用代理无法替所有客户端定义验收，持久化还涉及恢复、安全和生命周期。门禁只能阻止假完成，本身不保证产生更好的 action；若仍重复反馈，需要证明控制变化有推进效果。
- 可证伪实验：在同一客户端和验收器中对比现有 supervisor 与显式状态门禁；总预算、历史、工具、权限完全相同。记录独立交付率、连续停滞、完成延迟、待批准正确停机、重复副作用次数。若只提高“诚实失败率”，不宣称可用性改善。
- 许可：强制终答握手、默认接管客户端、任务状态存储、跨进程恢复、增加完成工具均须先获许可；不能本轮顺手落地。完成工具若采用，必须由客户端校验，不能只根据模型提交的 `completed=true` 放行。

## 6. 下一阶段实验设计与否决条件（本轮未执行）

建议先做无模型的固定事件／消息对照，再经许可做小范围真实模型配对实验，最后才讨论新的长程测评；不先用更长预算掩盖同一个循环。

| 对照用例 | 必须保持的结果 |
| --- | --- |
| 普通问答，即便请求携带工具定义 | 可普通终答，不被全局强制调用工具 |
| 真实工程缺口、参数和权限齐全 | 在预算内出现与缺口相关的有效操作并最终通过独立验收；只给计划失败 |
| 缺必需输入／权限明确拒绝 | 允许 blocked/needs-approval／拒绝停止；不猜参数、不换工具绕过权限 |
| 工具调用已交付，后台仍运行 | 跟随工具完成机制；不重发，不把启动回执当完成 |
| 已成功的写入／外部副作用，随后任务继续 | 复用真实回执，零重复副作用；生成新的 ID 不能洗掉重放问题 |
| 返回未知、控制器未证明停稳 | 停止并核对，不以“重试一次”掩盖可能已执行 |
| 只读路径相同但内容变化 | 不误判为完全相同观察；重复检测是诊断／状态信号，不是全局禁用 read |
| 整批含坏参数、其他调用合法 | 整批不交付；仅对未交付批次有限纠错，不放宽参数校验 |
| 字节／语义边界对照带附件、乱序结果 | 保留完整历史、附件、call/result 身份和错误属性；摘要不是历史替代品 |
| 验收通过后仍有未停稳写操作 | 不过早发布完成；后续修改须使旧验收证据失效并重新核验相关范围 |

主要指标必须是**真实交付率和非预期停顿**，辅助指标才是 action 率、协议合法率、监督反馈数。至少同时报告：无人工干预完成与分段恢复完成、每任务截止时间和调用预算、有效动作前的计划 stop 次数、重复观察次数、重复副作用次数、普通问答误强制率、阻塞／拒绝正确停止率、首次流式输出延迟与最终完成延迟。学校上游故障单独列出，不能简单删样或归罪模型。

失败判据：任何未知参数猜测、已交付工具盲目重放、权限绕过、完整历史／附件丢失、取消流式、验收器被模型修改、把预算耗尽或门禁拒绝算成功，均不能作为本项目可靠性收益。

## 7. 实施许可清单与本轮交付边界

本轮只交付此调查，不声称 H1/H2/H3 已成立，不声称任何候选已实现或已通过实验。下一轮可按用户已明确的调查方向推进无损审计与合成夹具实验；不为每条普通诊断重复索要确认。以下实质变化仍须单独说明并征得许可：

- 采集真实用户内容、扩大日志保留范围，或超出既定预算的大规模真实模型对照；合成夹具也须明确模型、次数和时限，不能默认无限长测。
- B 是否引入可选 action-or-finish 接口、局部 required 及其解除条件；不全局修改 auto。
- C 是否要求客户端完成握手、增加任务状态持久化和验收接入；普通客户端缺少该接入时不能承诺同等可靠性。
- 是否扩展真实阻塞状态与用户批准流；不把“继续直到成功”解释为无限预算或权限授权。

下一阶段应先回答“哪种最小控制变化在相同预算下提高了真实交付，并且不破坏问答、流式、安全和回执语义”，而不是再次只证明监督器知道任务没完成。
